# V4.0 接口定义清单

> 依据：《需求设计文档.md》V4.0 第 2.5 节
> 适用：实验室开放预约与使用记录管理系统，本轮为**增量接口清单**，未列出的接口沿用底版定义不变
> 统一返回：`{ "code": 200, "message": "操作成功", "data": {} }`
> 鉴权：所有接口需 `Authorization: Bearer <token>`（除登录/注册）

---

## 0. 角色与鉴权约定

| 角色 | role | 常量 | 说明 |
|------|------|------|------|
| 学生 | 0 | `Constants.ROLE_STUDENT` | 现有 |
| 实验室管理员 | 1 | `Constants.ROLE_ADMIN` | 现有 |
| 教师 | 2 | `Constants.ROLE_TEACHER` | **V4.0 新增** |

**鉴权标记说明**：
- 🟢 登录即可（任意角色）
- 🔵 教师或管理员（role ∈ {1,2}）
- 🔴 仅管理员
- ⚪ 无需登录

## 1. 用户与角色模块

### 1.1 新增用户（🔴 仅管理员）

```
POST /api/user/manage
```

**请求体**
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| username | string | 是 | 登录账号，唯一 |
| password | string | 是 | 明文传输，后端 BCrypt 加密；长度 ≥ 6 |
| name | string | 是 | 真实姓名 |
| role | int | 是 | 0-学生，1-管理员，2-教师 |
| studentNo | string | 条件 | role=0 或 2 时必填（学号/工号） |
| phone | string | 否 | 手机号 |
| email | string | 否 | 邮箱 |

**响应** `Result<Void>`

**错误码**
| code | 场景 |
|------|------|
| 400 | 账号已存在 / 参数缺失 / 密码过短 |
| 403 | 非管理员调用 |

**实现要点**：复用 `UserServiceImpl` 的 BCrypt 加密与唯一性校验逻辑，与 `register` 共用私有方法，避免逻辑分叉。

---

### 1.2 角色变更（🔴 仅管理员）

```
PUT /api/user/manage/{id}/role
```

**请求体**
```json
{ "role": 2 }
```

**校验规则**
1. role 必须是 0/1/2 之一
2. **不能修改自己的角色**（防止管理员把自己降级后无人可管）
3. 不能修改 `username = 'admin'` 的超级管理员角色（建议）

**响应** `Result<Void>`

**副作用**：角色变更后需删除该用户的 Redis 状态缓存，并使其现有 Token 失效（下次请求重新校验角色）。

---

### 1.3 登录（改造，⚪ 无需登录）

```
POST /api/user/login
```

**变更点**：`LoginDTO.role` 的取值范围由 `{0,1}` 扩展为 `{0,1,2}`。

> 现有实现 `UserServiceImpl` 已做 `user.getRole() != dto.getRole()` 的比对，**无需改逻辑**，只需放开 DTO 的取值校验与前端单选项。

### 2.3 实验室占用总览（**V4.0 新增**，🔵 教师/管理员）

```
GET /api/classroom/occupancy?date=2026-03-15&building=实验楼A
```

**用途**：教师端「实验室占用总览」页的数据源。展示某日全部实验室的分时段占用与剩余容量。

**查询参数**
| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| date | string | 是 | 日期 yyyy-MM-dd |
| building | string | 否 | 楼栋过滤 |
| type | int | 否 | 实验室类型过滤 |

**响应** `Result<List<OccupancyVO>>`

```json
{
  "code": 200,
  "message": "操作成功",
  "data": [
    {
      "classroomId": 1,
      "name": "计算机网络实验室",
      "building": "实验楼A",
      "roomNo": "A-301",
      "capacity": 40,
      "slots": [
        {
          "openTime": "08:00",
          "closeTime": "12:00",
          "slotCapacity": 40,
          "usedPeople": 15,
          "remainingPeople": 25,
          "reservationCount": 2
        }
      ]
    }
  ]
}
```

**口径说明**
- `usedPeople` = 该时段内重叠的**已通过(1)** 预约的 `people_count` 之和
- `remainingPeople` = `slotCapacity - usedPeople`，下限 0
- 无开放时段配置的实验室 `slots` 返回空数组
- 该接口**只读**，不含待审核预约（待审核不占位）

### 3.2 新增时段（🔴）

```
POST /api/slot
```

**请求体**
```json
{
  "classroomId": 1,
  "startDate": "2026-03-01",
  "endDate": "2026-05-31",
  "weekDays": "1,2,3,4,5",
  "openTime": "08:00",
  "closeTime": "12:00",
  "slotCapacity": 40,
  "remark": "工作日上午"
}
```

**校验规则（逐条硬性，任一条失败即拒绝）**
| # | 规则 | 错误提示 |
|---|------|----------|
| 1 | classroomId 对应的实验室必须存在且 status=1 | 实验室不存在或已停用 |
| 2 | `startDate ≤ endDate` | 开放结束日期不能早于开始日期 |
| 3 | `weekDays` 为 1-7 的逗号分隔数字，去重后非空 | 可预约星期格式不正确 |
| 4 | `openTime < closeTime` | 开放时段开始时间必须早于结束时间 |
| 5 | `slotCapacity ≥ 1` 且 `≤ classroom.capacity` | 时段人数上限不能超过实验室容量 |
| 6 | 同一实验室、同一日期区间内，**时段不重叠**（重叠公式同规则 1，按 open_time/close_time 判定），且 **weekDays 有交集** | 与已有时段「08:00-12:00」重叠，请调整 |

**响应** `Result<Void>`

---

### 3.3 编辑时段（🔴）

```
PUT /api/slot/{id}
```

**请求体**：同 3.2（不含 classroomId，不允许跨实验室移动）

**额外校验**：若该时段已被**已通过(1)** 的预约使用，且修改后会使 `slot_capacity < 已占用人数`，拒绝并提示「该时段已有 N 人预约，上限不能低于该值」。

---

### 3.4 删除时段（🔴）

```
DELETE /api/slot/{id}
```

**校验**：该时段下存在**未过期**的待审核/已通过预约时，**禁止物理删除**，提示「该时段存在 N 条有效预约，请先停用而非删除」。

**响应** `Result<Void>`

---

### 3.5 批量生成时段（🔴）

```
POST /api/slot/batch
```

**请求体**
```json
{
  "classroomId": 1,
  "startDate": "2026-03-01",
  "endDate": "2026-05-31",
  "weekDays": "1,2,3,4,5",
  "slotCapacity": 40,
  "timeWindows": [
    { "openTime": "08:00", "closeTime": "12:00" },
    { "openTime": "14:00", "closeTime": "18:00" }
  ]
}
```

**响应** `Result<Integer>`（返回生成条数）

**实现要点**：整批在一个事务内，任一 window 校验失败整批回滚。

---

### 3.6 查询某实验室可约时段与剩余容量（🟢 学生/教师端）

```
GET /api/slot/classroom/{classroomId}?date=2026-03-15
```

**用途**：实验室详情页与预约弹窗的数据源，展示当天的可约时段、上限、已占用人数、剩余人数。

**响应** `Result<List<AvailableSlotVO>>`

```json
{
  "code": 200,
  "message": "操作成功",
  "data": [
    {
      "slotId": 1,
      "openTime": "08:00",
      "closeTime": "12:00",
      "slotCapacity": 40,
      "usedPeople": 15,
      "remainingPeople": 25,
      "bookable": true,
      "reason": ""
    }
  ]
}
```

**`bookable=false` 的 reason 取值**
| reason | 场景 |
|--------|------|
| 日期不在开放范围 | date 早于 startDate 或晚于 endDate |
| 该日不开放 | 星期不在 weekDays 内 |
| 时段已结束 | 当天且当前时刻已过 closeTime |
| 剩余容量不足 | remainingPeople = 0 |

## 4. 预约模块（改造）

### 4.1 提交预约（改造，🟢）

```
POST /api/reservation
```

**请求体变更**：新增必填字段 `peopleCount`。

```json
{
  "classroomId": 1,
  "reserveDate": "2026-03-15",
  "startTime": "08:00",
  "endTime": "10:00",
  "peopleCount": 5,
  "purpose": "课程实验"
}
```

**校验链（顺序执行，任一失败即返回）**
| # | 校验 | 依据 | 错误提示 |
|---|------|------|----------|
| 1 | `peopleCount ≥ 1` | 规则 2 | 使用人数至少为 1 人 |
| 2 | `peopleCount ≤ classroom.capacity` | 规则 2 | 使用人数超出实验室容纳上限（{capacity} 人） |
| 3 | 日期星期在开放范围 `weekDays` 内 | 规则 3 | 该日期实验室不开放 |
| 4 | `startTime/endTime` 完整落在同一开放窗口内 **且仍在 08:00-22:00 基准窗口内** | 规则 3 | 预约时间超出实验室开放时段 |
| 5 | 非过去日期、今天须晚于当前时刻 | 规则 3 | 不能预约已过去的时段 |
| 6 | 时长 ≤ `Constants.MAX_RESERVATION_HOURS` | 规则 3 | 单次预约不能超过 N 小时 |
| 7 | **冲突检测**（已通过预约时间重叠） | 规则 1 | 该时段已被预约 |
| 8 | **容量检测**（重叠已通过预约人数之和 + 本次 ≤ slot_capacity） | 规则 2 | 该时段剩余容量不足，仅剩 N 人 |

> 第 7、8 步必须在 `classroomMapper.selectOne(...FOR UPDATE)` 锁定实验室行之后执行，保证「检测 + 插入」原子。

---

### 4.2 冲突与容量预校验（改造，🟢）

```
GET /api/reservation/check-conflict?classroomId=1&reserveDate=2026-03-15&startTime=08:00&endTime=10:00&peopleCount=5
```

**变更点**：新增查询参数 `peopleCount`；返回体新增容量字段。

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "conflict": false,
    "conflictMessage": "",
    "capacityEnough": true,
    "slotCapacity": 40,
    "usedPeople": 15,
    "remainingPeople": 25,
    "capacityMessage": ""
  }
}
```

**前端用法**：选择时段与人数的瞬间调用，`conflict || !capacityEnough` 时禁用「提交预约」按钮。

---

### 4.3 取消预约（改造，🟢）

```
PUT /api/reservation/{id}/cancel
```

**请求体变更**：`reason` 改为必填。

```json
{ "reason": "课程临时调整" }
```

**⚠️ 破坏性变更提示**：现有 `ReservationServiceImpl.cancelReservation(Long id)`（第215行）**无 reason 参数**，需改为 `cancelReservation(Long id, String reason)`，Controller 同步从 `@PathVariable only` 改为收 `@RequestBody`。前端 `web/src/api/reservation.js` 的 `cancelReservation` 调用点须一并改造。

**校验链**
1. 预约存在且属于当前用户（管理员可代取消）
2. 当前状态 ∈ {待审核(0), 已通过(1)}，否则「该预约当前状态不可取消」
3. 距开始时间 ≥ 1 小时（规则 5），否则「距预约开始不足 1 小时，无法取消，请联系管理员」
4. 写入 `status=3`、`cancel_reason`、`cancel_time`、`update_time`

---

### 4.4 审核通过/驳回（改造，🔴）

```
PUT /api/reservation/{id}/audit
POST /api/reservation/batch-audit
```

**变更点（只在审核通过路径上）**：现有逻辑是「复查时间冲突」，**追加**「复查容量」：
通过前重新计算该时段已通过预约的 `people_count` 之和，加上本条预约的 `people_count`，若超过 `slot_capacity`，则拒绝通过并提示「该时段剩余容量不足，仅剩 N 人，本条需 M 人」。

> 复核必须在既有的 `FOR UPDATE` 锁教室行之后、`LambdaUpdateWrapper` 条件更新之前执行。

### 5.2 登记使用（🔴）

```
POST /api/usage
```

**请求体**
```json
{
  "reservationId": 101,
  "actualPeople": 4,
  "useStatus": 1,
  "checkRemark": "正常使用，4 人到场"
}
```

**校验链**
| # | 规则 | 错误提示 |
|---|------|----------|
| 1 | 预约存在且 `status = 1` | 仅已通过的预约可登记使用 |
| 2 | 该预约**未有**使用记录（`uk_reservation` 唯一约束兜底） | 该预约已登记，请勿重复提交 |
| 3 | `useStatus ∈ {1,2,3}` | 使用状态取值非法 |
| 4 | `useStatus = 3`（失约）时 `actualPeople` 必须为 0 | 失约记录实际使用人数应为 0 |
| 5 | `useStatus ≠ 3` 时 `1 ≤ actualPeople ≤ peopleCount` | 实际使用人数不能超过预约人数（{peopleCount} 人） |
| 6 | `useStatus = 2`（部分使用）时 `actualPeople < peopleCount` | 部分使用时实际人数应少于预约人数，请改用「正常使用」 |

**响应** `Result<Void>`

**副作用**：失效统计模块 Redis 缓存（复用 `redisCache.invalidateBusinessCaches()`）。

---

### 5.3 批量登记失约（🔴）

```
POST /api/usage/batch-noshow
```

**请求体**
```json
{ "reservationIds": [101, 102, 103] }
```

**行为**：对每个 id 生成 `actual_people=0, use_status=3` 的登记记录，批内任一条不满足 5.2 的规则 1/2 则整批回滚并指名 ID。

**响应** `Result<Integer>`（成功登记条数）

---

```
GET /api/usage/manage?page=1&size=10&startDate=2026-03-01&endDate=2026-03-31&classroomId=1&useStatus=3&userName=张三
```

**响应** `Result<PageResult<UsageRecordVO>>`，字段含 `usage_record` 全部字段 + 关联的预约与用户冗余展示字段。

```
GET /api/usage/export?startDate=...&endDate=...&classroomId=...&useStatus=...
```

```json
{
  "todayReservationCount": 12,
```

|----------|------|
| `pendingUsageCount` | 已通过且已结束但未登记的预约数（与 5.1 同口径） |
| `todayActualPeople` | 今日使用记录中 `use_status ≠ 3` 的 `actual_people` 之和 |

---

### 6.2 实际使用人数统计（**V4.0 新增**，🔴）

```
GET /api/stats/actual-usage?startDate=2026-03-01&endDate=2026-03-31
```

**用途**：看板第 4 张图的数据源。

**响应** `Result<List<ActualUsageVO>>`

```json
{
  "code": 200,
  "message": "操作成功",
  "data": [
    {
      "classroomId": 1,
      "name": "计算机网络实验室",
      "building": "实验楼A",
      "roomNo": "A-301",
      "reservationCount": 20,
      "reservedPeople": 85,
      "actualPeople": 72,
      "attendanceRate": 84.7,
      "noShowCount": 3
    }
  ]
}
```

**口径**
- `reservationCount`：区间内已通过预约数
- `reservedPeople`：这些预约的 `people_count` 之和
- `actualPeople`：对应使用记录中 `use_status ≠ 3` 的 `actual_people` 之和
- `attendanceRate` = `actualPeople / reservedPeople × 100`，保留 1 位
- `noShowCount`：`use_status = 3` 的记录数

---

### 6.3 使用率（改造口径说明，🔴）

```
GET /api/stats/usage-rate?startDate=...&endDate=...
```

**变更点**：接口路径与响应结构不变，仅在 `UsageRateVO` 增加两个补充字段：

```json
{
  "classroomId": 1,
  "name": "...",
  "usageRate": 62.5,
  "approvedHours": 87.5,
  "actualUsageRate": 55.2,
  "noShowRate": 11.4
}
```

| 字段 | 口径 |
|------|------|
| `usageRate` | 现有口径不变（已通过时长 / 可预约时长） |
| `actualUsageRate` | 实际使用过的预约占用时长 / 可预约时长（`use_status ≠ 3` 的记录对应预约） |
| `noShowRate` | 失约记录数 / 已通过预约数 × 100 |

## 9. 前端路由改造

```js
// web/src/router/index.js
roleHome = { 0: '/student/home', 1: '/admin/home', 2: '/student/home' }

// 学生/教师共用端
{ path: '/student', meta: { requiresAuth: true, roles: [0, 2] }, children: [...] }

// 教师专属页（在 /student 下新增一条）
{
  path: 'occupancy',
  name: 'LabOccupancy',
  component: () => import('@/views/student/LabOccupancy.vue'),
  meta: { requiresAuth: true, roles: [0, 2] }   // 学生也可访问，教师菜单才显示入口
}
```

> 决策说明：占用总览页**路由对学生也开放**（roles [0,2]），只是**侧边栏菜单仅对教师渲染**。理由：学生一样有「看整个楼层排期」的合理需求，多开放一个只读页零成本；若你要求严格隔离，改成 `roles: [2]` 即可。
